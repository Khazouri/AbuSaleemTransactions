# Deploying the SPA to cPanel

The frontend is a static bundle. cPanel serves it with plain Apache — there is
no Node process on the server, and nothing is compiled there.

## The one mistake that produces a black screen

> `Uncaught TypeError: Failed to resolve module specifier "vue". Relative
> references must start with either "/", "./", or "../".`

This means the **source tree was uploaded instead of the build output**.

`frontend/index.html` — the source one — ends with:

```html
<script type="module" src="/src/main.js"></script>
```

`/src/main.js` starts with `import { createApp } from 'vue'`. That is a *bare*
module specifier: it names a package, not a path. The Vite dev server rewrites
those into real URLs as it serves each file; Apache does no such thing, so the
browser hits the first import, cannot turn `"vue"` into a URL, and stops. The
app never mounts, which is the black screen.

`dist/index.html` is a *different file*, generated by the build. It points at a
fingerprinted, fully bundled `/assets/index-*.js` with every import already
resolved. **Only `dist/` is deployable.** Never upload `src/`, `node_modules/`,
`package.json`, or the root `index.html`.

## Deploy

1. **Set the API URL.** Edit `VITE_API_BASE_URL` in
   [.env.production](.env.production). It is baked into the bundle at build
   time — editing it on the server has no effect, so this must happen *before*
   step 2. Use `https` if the site is served over `https`; a mixed-content
   request is blocked by the browser before it is sent, which looks exactly
   like an API outage.

2. **Build**, from `frontend/`:

   ```bash
   npm ci
   npm run build
   ```

3. **Upload the *contents* of `dist/`** into the document root of the domain or
   subdomain (`public_html/`, or whatever folder the subdomain points at) — the
   files themselves, not the `dist` folder. You should end up with:

   ```
   public_html/
   ├── .htaccess
   ├── index.html
   ├── favicon.svg
   ├── icons.svg
   └── assets/
   ```

   **Check that `.htaccess` made it.** It is a dotfile, and cPanel's File
   Manager hides dotfiles until you tick *Show Hidden Files* in Settings —
   several FTP clients skip them silently too. Without it, the site loads but
   every refresh on a sub-route 404s (see below).

4. **Point the API at the SPA.** In the *Laravel* `.env`, set

   ```
   FRONTEND_URL=https://the-spa-origin.example.com
   ```

   `config/cors.php` reads it. The SPA and API are on different origins, so
   without this every request fails CORS preflight and the login screen just
   spins. Run `php artisan config:clear` after changing it.

## Why `.htaccess` is required

The router uses `createWebHistory()`, so `/departments` and `/meetings/12` are
real URLs users can bookmark and refresh — but there is no such file on disk.
Apache returns 404 unless told to hand back `index.html` and let the router
resolve the path. That rule lives in [public/.htaccess](public/.htaccess),
which Vite copies verbatim into `dist/` on every build.

It has no `RewriteBase`, so the same file works at a domain root, on a
subdomain, or in a subfolder without editing.

## Subfolder deploys need one more change

The built asset paths are absolute (`/assets/index-*.js`). At a domain root or
on a subdomain that is correct. If the app is served from a **subfolder**
(`example.com/app/`), those paths resolve to the domain root and 404 — the
symptom is a blank page with failed asset requests rather than the module error
above. Fix it in `vite.config.js` and rebuild:

```js
export default defineConfig({
  base: '/app/',
  plugins: [vue()],
})
```

## Checks when something looks wrong

| Symptom | Cause |
| --- | --- |
| `Failed to resolve module specifier "vue"` | Source uploaded, not `dist/`. |
| Blank page, 404s on `/assets/*` | Subfolder deploy without `base` set. |
| Home page works, refresh on any other route 404s | `.htaccess` missing or `mod_rewrite` off. |
| Login spins; console shows a CORS error | `FRONTEND_URL` not set in the Laravel `.env`. |
| Login fails; console shows a mixed-content warning | `VITE_API_BASE_URL` is `http` on an `https` site. |
| Old version persists after redeploy | `index.html` was cached; the `Cache-Control` rules in `.htaccess` prevent this. |
